# ماژولار کردن اکوسیستم وستو برای سالسا

هدف این نسخه، تحویل همان کد، صفحه‌ها و گردش کار فعلی وستو به رستوران‌های دیگر است. طراحی صفحه‌ها و منوهای موجود بازنویسی نشده‌اند. دادهٔ هر رستوران جدا است؛ مشتری تازه، غذا، سفارش، مشتری، موجودی و سابقهٔ فروش وستو را دریافت نمی‌کند.

## ساختار اجرا

این سیستم یک برنامهٔ واحد با ماژول‌های مستقل است. هر ماژول مالک پیاده‌سازی خود است؛ نصب رستوران جدید به معنای ساخت نسخهٔ کپی‌شدهٔ برنامه نیست. سالسا هویت رستوران، دامنه، اشتراک، نقش کاربران و نسخهٔ تخصیص‌یافته را مدیریت می‌کند. وستو همچنان مشتری مرجع و محیط طراحی محصول است.

| پوشه | مسئولیت |
| --- | --- |
| `platform_core` | ورود، هویت، نقش، پوستهٔ مشترک، رویدادها و زیرساخت |
| `menu_qr` | منوی آنلاین و سه‌بعدی، محصولات، گزینه‌های غذا، ترجمه و چاپ |
| `pos` | سفارش، صندوق، تسویه، رسید و گردش پرداخت عملیاتی |
| `floor` | سالن، میزها و ترمینال گارسون |
| `kds` | صف و گردش کار آشپزخانه |
| `reservations` | رزرو و صف انتظار |
| `delivery` | محدوده‌ها و عملیات پیک |
| `payments` | اتصال و وضعیت پرداخت |
| `accounting` | موتور مالی، دفتر، اسناد و رابط حسابداری |
| `inventory` | انبار، رسپی، مصرف و موجودی |
| `crm` | مشتریان، وفاداری، کیف پول، کمپین و پیامک |
| `multi_branch` | مدیریت شعب |
| `website_brand` | محتوا، ظاهر، رسانه و مشخصات مجموعه |
| `analytics` | بازدید، تحلیل و گزارش‌ها |

هر پوشه شامل `module.json`، ورودی `index.js`، کد `server` و/یا `frontend` و خروجی نسخهٔ منتشرشده در `releases` است. ماژول‌ها ممکن است از قرارداد مالی، هویت یا دادهٔ مشترک استفاده کنند؛ استقلال پوشه به معنای اجرای جداگانهٔ سرورها نیست.

۲۳۰ فایل موجود به محل مالک خود منتقل شده‌اند؛ ۱۲ فایل اجرای نما نیز از پوستهٔ ادمین استخراج شده‌اند. مسیرهای قدیمی لینک نسبی به همین پیاده‌سازی هستند تا URLها، ابزارهای ساخت و مصرف‌کننده‌های قبلی کار کنند. تنها یک نسخهٔ قابل ویرایش از هر فایل وجود دارد. خروجی‌های `releases` نسخهٔ ثابت برای تحویل هستند و محل ویرایش روزانه نیستند. لینوکس VPS از این لینک‌ها پشتیبانی می‌کند؛ بسته‌بندی static نیز محتوای لینک را کپی می‌کند.

`server/server.js` همچنان ترتیب ثبت مسیرها، middlewareها، اتصال داده و برخی کمک‌تابع‌های مشترک را ترکیب می‌کند. ۲۱۸ بدنهٔ مسیر HTTP در پوشهٔ ماژول مالک قرار گرفته‌اند. مسیرهای مستقل موتور حسابداری، Finance V2 و Admin V2 در فایل‌های منتقل‌شدهٔ خود ثبت می‌شوند. ۳۷ بدنهٔ نمای ادمین در `frontend/admin-views.js` ماژول‌ها قرار دارند؛ پوستهٔ ادمین فقط ثبت، ناوبری و context مشترک را ترکیب می‌کند. فایل‌های `http-routes.json`، `admin-views.json` و `source-map.json` مالکیت و اثر انگشت استخراج را نگه می‌دارند.

## سه قرارداد مستقل

۱. **ثبت داده:** ثبت سفارش، دریافت، فروش قطعی و رویداد مالی به خرید رابط حسابداری وابسته نیست. خاموش بودن اشتراک حسابداری باعث حذف یا توقف این تاریخچه نمی‌شود. کنترل‌های واقعی دورهٔ مالی، صحت مبلغ، ثبت پایدار، rollout و جلوگیری از تکرار همچنان برقرارند؛ سند نامعتبر به‌صورت ساختگی ثبت نمی‌شود و رویداد مسدودشده برای رسیدگی حفظ می‌شود.

۲. **دسترسی:** قابلیت خریداری‌شده و نقش کاربر هر دو لازم‌اند. پنهان‌کردن منو به‌تنهایی مجوز امنیتی نیست. APIهای اصلی و مسیرهای قدیمی حسابداری نیز از همان کنترل اشتراک عبور می‌کنند. انقضا، لغو یا غیرفعال‌کردن اشتراک، دادهٔ ذخیره‌شده را حذف نمی‌کند. پاسخ صندوق اطلاعات عملیاتی پرداخت را نگه می‌دارد؛ جزئیات داخلی سند حسابداری برای مشتری فاقد اشتراک حذف می‌شود. داشبورد چنین مشتری‌ای تحلیل مالی و میان‌بر حسابداری را نمایش نمی‌دهد.

۳. **نسخه:** انتخاب نسخه با فعال‌کردن اشتراک تفاوت دارد. تغییر نسخه هیچ ماژولی را نمی‌فروشد یا فعال نمی‌کند و هیچ سابقه‌ای را پاک نمی‌کند.

## رستوران تازه

`createBlankTenantDb` دادهٔ تجاری خالی، هویت مستقل و نسخه‌های واقعی ماژول‌ها را می‌سازد. حسابداری در پس‌زمینه برای capture آماده است؛ راه‌اندازی شعبه، تنظیمات مالی معتبر و دورهٔ مالی باید با دادهٔ همان رستوران انجام شود. غذا و قیمت نمونهٔ وستو، قواعد مالیاتی فرضی یا شعبهٔ ساختگی وارد دادهٔ مشتری نمی‌شوند.

Host باید در مرجع کنترل ثبت شده باشد؛ نام دامنه یا header دلخواه، مجوز ساخت مشتری جدید نیست. نشست کاربر به tenant امضا شده و در دامنهٔ مشتری دیگر پذیرفته نمی‌شود. bootstrap استاتیک مشتری جدید از دادهٔ همان درخواست تولید می‌شود تا منوی آفلاین وستو وارد مشتری دیگر نشود. صفحهٔ سه‌بعدی بدون محصولات، کارت‌های غذایی پیش‌فرض را نمایش نمی‌دهد و همان پوسته را نگه می‌دارد.

## انتشار و تخصیص نسخه

نسخهٔ واقعی فعلی همهٔ ماژول‌ها `1.0.0` است؛ نسخه‌های ۲ و ۳ تا زمان ساخت و انتشار فایل واقعی در انتخاب‌گر ظاهر نمی‌شوند.

```sh
npm run modules:verify
npm run test:modules
npm run modules:build
node scripts/build-westo-module-release.js menu_qr 2.0.0
```

آخرین دستور فقط پس از آماده‌کردن تغییر واقعی و آزمون سازگاری نسخهٔ جدید اجرا می‌شود. `release.json` قرارداد API، نسخه، توضیح و SHA-256 فایل‌ها را نگه می‌دارد. انتشار دوبارهٔ همان نسخه با محتوای متفاوت رد می‌شود. نسخهٔ تخصیص‌یافته از فایل ثابت همان release سرو می‌شود. نمونهٔ محلی وستو که نسخه‌ای pin نشده دارد، برای طراحی محصول از فایل‌های جاری استفاده می‌کند.

این releaseها نسخهٔ رابط و دارایی‌های مرورگر با API مشترک `westo-v1` هستند. اجرای موتورهای backend در برنامهٔ مشترک باقی می‌ماند؛ اجرای هم‌زمان backend ناسازگار نسخهٔ ۲ و ۳ برای مشتریان مختلف در این تغییر پیاده نشده است. تغییر ناسازگار backend به قرارداد و مهاجرت نسخهٔ جدید نیاز دارد. دادهٔ مشتری از release جدا نگهداری می‌شود. bootstrap تولیدشدهٔ منو artifact نسخه نیست و در نسخه‌ها کپی نمی‌شود؛ مشتری تازه آن را از دادهٔ خالیِ خودش می‌گیرد.

مسیرهای Control Plane:

- `GET /api/control/policy/module-releases/:tenantId`: فهرست نسخه‌های واقعی و revision تخصیص.
- `PATCH /api/control/policy/module-releases/:tenantId/:moduleKey`: انتخاب نسخه با `version`، `expectedRevision` و `reason`؛ فقط نقش مجاز مدیریت پلتفرم.

تخصیص در transaction با قفل ردیف tenant و ثبت ممیزی انجام می‌شود. تعارض revision، نسخهٔ ناموجود، خرابی artifact یا نبود رسید ذخیره‌سازی به موفقیت تبدیل نمی‌شود. متادیتای مرجع tenant نسخه را در درخواست بعدی تعیین می‌کند. تغییر انتخاب در پنل، پس از بارگذاری دوبارهٔ مشتری دیده می‌شود؛ کش سرویس‌ورکر برای JS/CSS ابتدا نسخهٔ شبکه را بررسی می‌کند و در قطعی همان fallback آفلاین را حفظ می‌کند.

انتخاب‌گر کوچک نسخه داخل کارت‌های فعلی اشتراک سالسا اضافه شده است؛ صفحه یا منوی جدیدی برای وستو ساخته نشده. مسیر ۴۱۸۰ وستو و هر دو پوستهٔ مدیریت موجود حفظ شده‌اند. `start:godmode` و `start:full` پوستهٔ فعلی سالسا را روی ۳۰۵۰ اجرا می‌کنند. اجرای یکپارچه تنظیمات `.env.local` را در صورت وجود بارگذاری می‌کند تا وستو از پایگاه‌دادهٔ تنظیم‌شده استفاده کند؛ Control Plane روی ۳۰۶۱ است و نشانی API آن به پنل سالسا داده می‌شود. پوستهٔ قدیمی prototype همچنان برای اجرای مستقل در مخزن موجود است.

## راستی‌آزمایی این مرحله

- SHA منطقی ۲۱۸ بدنهٔ مسیر و ۳۷ نمای استخراج‌شده با نسخهٔ پیش از استخراج برابر است. helper آزمون، کد اجرایی فعلی ماژول را می‌خواند؛ نسخهٔ قدیمیِ کپی‌شده جای آن نیست.
- آزمون HTTP با دو Host ثبت‌شدهٔ آزمایشی، دادهٔ موقت و پورت آزاد: منوی خالی، دارایی نسخهٔ ۱، عدم افشای فایل server، رد نشست مشتری دیگر، رد API حسابداری و KDS فاقد اشتراک.
- ثبت فروش تاریخی مرداد، replay بدون تکرار، ثبت و تسویهٔ واقعی صندوق در حالی که حسابداری غیرفعال است، ذخیرهٔ سند در فایل موقت، بازشدن همان سابقه پس از فعال‌سازی، و حفظ داده بعد از انقضا.
- ۳۲ آزمون متمرکز ماژول/صندوق/تراکنش/رویداد مالی با سرور HTTP واقعی موفق شدند. مجموعهٔ عمومی خطاهای از قبل موجود دارد؛ گزارش دقیق در `VERIFICATION.md` ثبت شده است.
- نمونهٔ آزمایشی در مرورگر بررسی شد؛ ظاهر فعلی و منوی خالی حفظ شده و گزینه‌های خریداری‌نشده و پنل مالی داشبورد پنهان هستند. سرور و فایل دادهٔ لایو تغییر داده نشدند.

## مرحلهٔ بعد: میزبانی واقعی

تنظیمات DNS، وب‌سرور، VPS و deployment موجود حفظ شده‌اند. این تغییر، اثبات اتصال دامنهٔ عمومی یا آماده‌بودن عملیات production نیست. مرحلهٔ بعد روی زیرساخت واقعی اجرا می‌شود:

۱. اتصال دامنه، اثبات مالکیت، بررسی DNS از resolverهای عمومی و ثبت Host تأییدشده.
۲. مسیر wildcard/دامنهٔ اختصاصی، HTTPS خودکار، تمدید گواهی و جلوگیری از تحویل tenant پیش‌فرض به Host ناشناخته.
۳. PostgreSQL پایدار و مرجع Control Plane، جداسازی داده، secrets، backup/restore و ذخیرهٔ فایل هر رستوران.
۴. آزمون provision مشتری خالی تا ورود مالک، تخصیص ماژول، ثبت صندوق، capture حسابداری و فعال‌سازی دیرهنگام روی دامنهٔ واقعی.
۵. آزمون ارتقا/برگشت نسخه، مشاهده‌پذیری، سلامت سرویس‌ها و ظرفیت VPS پیش از پذیرش مشتری.

تا اجرای این آزمون‌ها روی زیرساخت واقعی، وضعیت آمادگی production از موفقیت آزمون محلی نتیجه‌گیری نمی‌شود.
